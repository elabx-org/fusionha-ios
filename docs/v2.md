# fusionha v2

v2 is a second app built from this repo and installed beside v1. v1 keeps
shipping, unchanged, while v2 is rebuilt screen by screen from the approved v2
mock (owner, 2026-11-05). Both apps come from `main` and ship in the same
Feather source.

## The two products

| | v1 | v2 |
|---|---|---|
| Home-screen name | fusionha | fusionha v2 |
| Scheme / target | `Fusionha` | `FusionhaV2` |
| Bundle ids | `org.elabx.fusionha`, `.widgets`, `.notification-service` | `org.elabx.fusionha.v2`, `.v2.widgets`, `.v2.notification-service` |
| App Group | `group.org.elabx.fusionha` | `group.org.elabx.fusionha.v2` |
| Keychain group | `$(AppIdentifierPrefix)org.elabx.fusionha.shared` | `$(AppIdentifierPrefix)org.elabx.fusionha.v2.shared` |
| Keychain services | `org.elabx.fusionha.*` | `org.elabx.fusionha.v2.*` |
| URL scheme | `fusionha://` | `fusionha2://` |
| Version | 1.1.<CI run> | 2.0.<CI run> |
| Icon | `AppIcon` | `AppIconV2` (`scripts/make_v2_icon.py`) |
| Push | on | built, waits for the server's topic or the cutover (see below) |

Each app signs in on its own. Signing out of v2 never touches v1: v2 has its own
App Group, its own keychain services, and no `TEAMID.*` wildcard keychain group
(only v1 keeps that legacy fallback).

## How the code is split

- **`AppIdentity`** (`Packages/FusionhaKit/Sources/FusionhaKit/AppIdentity.swift`)
  reads `FusionhaAppGroup`, `FusionhaKeychainNamespace` and `FusionhaURLScheme`
  from the running bundle's Info.plist. A missing key falls back to v1's value,
  so v1's Info.plists don't carry the keys. Every App Group, keychain service,
  team keychain group and deep link comes from it, never from a literal.
- **Entry points.** `App/FusionhaApp.swift` (v1) and `App/V2/FusionhaV2App.swift`
  (v2) are the only `@main`s. Both wrap `AppSceneContent`: the screenshot
  galleries, sign-in gate, Duo harness, deep links and probes. v1 passes
  `RootView`, v2 passes `V2RootView`.
- **Targets** (`project.yml`). The v1 targets exclude `App/V2/**` and
  `Widgets/V2/**`. `FusionhaV2` compiles `App` (without `FusionhaApp.swift`)
  and `Shared`. `FusionhaV2Widgets` compiles `Widgets` and `Shared`. Both v2
  targets build with the `V2` compilation condition. Keep `#if V2` to a few spots
  in shared code. v2 screens are new files under `App/V2/` that reuse v1's
  stores and models.
- **Push (slice S16).** v2 has v1's push code and its own rich-push extension
  (`FusionhaV2NotificationService`, `org.elabx.fusionha.v2.notification-service`,
  the same `NotificationService/` sources). The server sends every push under one
  APNs topic (`ApnsStatus.topic`, v1's bundle id by default), and APNs rejects
  tokens from any other app. `App/PushAvailability.swift` therefore decides at
  run time, by identity, not `#if V2`: v1 always registers, as before; any other
  app asks for permission and registers only when the server's topic is its own
  bundle id (read on sign-in and in Settings › Notifications, and cached).
  Side by side, v2's This device card reads "Unavailable" and says which app
  the server pushes to. v2's app has no `aps-environment` yet, so it gets no
  token even if the topic is pointed at it; that entitlement comes with the
  cutover. v2's API token is named `fusionha v2 iOS · <device>` so the server's
  token list tells it apart from v1's.

## Cutover: v2 replaces v1 (owner, 2026-11-06)

Once v2 is complete it takes v1's place: installing it upgrades v1 in place and
keeps the sign-in, widgets and push. Nothing in v2's code names an id: App Group,
keychain namespace and URL scheme come from `AppIdentity` (Info.plist), push from
`PushAvailability` (bundle id), and the widget kinds (`Downloads`, `UpNext`,
`RecentlyAdded`, the stacks), Live Activity attributes and App Group keys are the
same sources as v1's. The cutover is a `project.yml` change only, and it needs the
owner (signing and ids):

- `FusionhaV2`: `PRODUCT_BUNDLE_IDENTIFIER: org.elabx.fusionha`; drop the
  `FusionhaAppGroup` / `FusionhaKeychainNamespace` / `FusionhaURLScheme` keys
  (v1's values are the fallback) or set them to v1's; URL type
  `org.elabx.fusionha` / `[fusionha]`; entitlements `aps-environment:
  development`, App Group `group.org.elabx.fusionha`, keychain
  `$(AppIdentifierPrefix)org.elabx.fusionha.shared`; `CFBundleDisplayName:
  fusionha`; `MARKETING_VERSION` above v1's last 1.1.N (2.0.N already is).
- `FusionhaV2Widgets`: `org.elabx.fusionha.widgets`, the same group, keychain and
  Info.plist keys as above.
- `FusionhaV2NotificationService`: `org.elabx.fusionha.notification-service`,
  the same group, keychain and Info.plist keys.
- Retire the v1 targets (`Fusionha`, `FusionhaWidgets`, `FusionhaNotificationService`)
  and the CI matrix leg, or keep v1 off the Feather source, so two apps never
  claim one id. The `#if V2` spots (token name, a few screens) stay as they are.

## Multiple windows (split screen)

v2 runs in several windows: the system split screen on the open iPhone Duo and
iPad-class multitasking. `UIApplicationSupportsMultipleScenes` is `true` for the
v2 app only; v1 stays single-window.

- **Session vs window.** `AppSession` (`App/AppSession*.swift`) is created once
  by the `@main` and holds what the app shares: the sign-in, the account, the
  library, the queue, the shell's badges and settings, setup progress, push and
  the Live Activity sync. Each window builds its own `AppModel` over it
  (`App/V2/Windows/V2Window.swift`): tab, search, open title and the Library /
  title split, sheets, pending links, selection, toasts and the title sheet's
  presence. Screens keep reading `model.library`, `model.queue` and the rest
  through get-only forwards (`AppModel+Session.swift`). v1 builds one session
  and one model, so its behaviour is unchanged.
- **Pollers run once.** A window holds a polling lease while its scene is
  active with its shell on screen (`ShellPresentations`). The queue, shell and
  setup loops run while any lease is held (`AppSession+Polling`). The shell's
  first account load and push registration run once per sign-in.
- **Links.** A notification tap, widget or Live Activity link opens in the
  window used last: the last to become active or key (`V2KeyWindowTracker`).
  If that window went to the background, the scene the system brought
  forward takes it. Every window prefers the app's own links and allows any
  other event (`handlesExternalEvents(preferring: ["fusionha2://"], allowing:
  ["*"])`), so neither a link nor a launch from the Home Screen icon opens a
  new window. Allowing only the links made each icon tap match no open window,
  and the system opened another one every time. CI's `v2 windows (iPad)` job
  checks it (`scripts/v2_scene_check.sh`).
- **Open in New Window.** In the poster's long-press sheet, the list row's
  menu and the title page's More menu. It calls `openWindow(value:)` with a
  `V2TitleWindow` (`WindowGroup(for:)`), and the new window opens that title
  through the deep-link path once. The item is hidden when
  `supportsMultipleWindows` is false.
- **Library filters follow the window.** Kind, version, status, sort, added
  and group live in `@SceneStorage`. A new window starts from the filters used
  last (written through to the old `UserDefaults` keys,
  `V2LibrarySceneFilters`). Density, the Duo layout and the Coming up row stay
  device-wide.
- **Shared on purpose.** Image and palette caches, `PaletteStore`, the
  setup pill's expanded / dismissed state and the queue's group memory are
  shared. Known follow-up: the same title open in two windows has two
  `DetailStore`s, so an edit in one refreshes the other only on its next load.

## Fold continuity (owner, 2026-11-06)

Folding or unfolding the iPhone Duo takes you to exactly the same place: the
same tab, pushed page, open title, pick, sheet and the row you were looking
at. A fold is a resize and the app keeps its scene, but v2 lays some state
out two ways (a right page open, a sheet or a pushed page folded), so the
state lives where both layouts read it. The pure rules are in FusionhaKit
(`FoldContinuity.swift`: `FoldPick`, `FoldRoute`, `FoldAnchorLog`,
`TriageQueueFocus.deckOrder`; `FoldPlaces.swift`: `FoldHeaderOffset`,
`FoldPagePlaces`, `AllTitlesPush`; unit-tested); the window holds the values
(`V2RootView`: `FoldKeep`, `V2TitleStacks`). v1 never sets `\.foldKeep` or
`stackPath`, so v1 is unchanged.

| Screen | Kept across the fold |
|---|---|
| Shell | Tab, open title (sheet folded, column open), each tab's own stack and state (the tab view keeps its identity across the split). |
| Title | Tab and scroll offset (v1's re-host), child sheets and drafts (`DetailHostGate`), and now the pushed season / episode pages: both hosts bind one per-window path (`TitlePageOverride.stackPath` → `V2TitleStacks`, writes only from the host on screen), and Next up's episode pushes onto it. The path goes when the title closes. Each pushed page's place rides in the same store (`V2TitleStacks.place`, `V2PagePlace`, written only by the page instance on screen): the season keeps the episode row under the eye line (`.foldPlaceRow`, restored once per page instance, under the line rather than at the top), the episode its tab, version and offset past its header (`FoldHeaderOffset`: the hero folded and the short header open differ in height). A pop drops the popped pages' places (`FoldPagePlaces`), so pushing a page again starts at its top. |
| Activity › Queue | The held download picked: its decision page open ⇄ its sheet folded (`foldPick`), and the row at the list's top (`FoldAnchor`: rows report when they reach the eye line, the resize scrolls that row back; off while the split's grip drags). |
| Held decision (close mid-decision, owner) | Folding with a decision open shows the same decision in its sheet with the same option picked and the same scroll; unfolding puts the page back the same way. The queue (never replaced by a fold) keeps them in `HeldDecisionDraft`, which page and sheet read at init; the scroll rides `keepsScrollOffset` (reports ignored until restored). No hinge-angle API. |
| History, Wanted, Tasks | The story / title / run picked: right page ⇄ sheet (`foldPick`; Wanted per tab). The row at the list's top by id (`V2ScopeList` runs Queue's `FoldAnchor`; rows mark themselves `.foldRow`). |
| Blocklist | The title open on the right page opens inline folded, and back. The row at the list's top, as History. |
| Audit, Indexers | v1's rows on v2's ground (`V2KeptScope`): nothing kept beyond the tab. |
| Manual Import | Its presentation swaps (sheet ⇄ both pages), so the scan, the draft choices, the list's scroll (`listY`) and the pushed pages live in `V2MIKept` (`FoldKeep`, dropped when Activity closes it). The split's open card ⇄ the phone's pushed page (`V2MIFoldRoute`). |
| Requests | The request focused in the open panes is the card in front of the folded deck, and deciding cards folded moves the focus (`InboxModel.focus`, `deckOrder`). |
| Add | Its presentation swaps too: query, kind, source, the pick and its setup (`AddFlow`), the request pick and the pushed preview ride in `AddFoldCarry`, taken back by the next host within 3 s; dropped when Add closes. |
| Settings | Already one split that collapses into the phone's push list (full-screen cover, never re-presented): the open panel and the panels pushed on it. The open Duo's Overview with nothing picked folds to the phone's home. |
| Discover, Calendar, Search | Already kept: query, tab, kind, mode, selected day and offset (`@State` in the tab, which keeps its identity); the hero carousel keeps its centred card (`scrollPosition(id:)`). |
| Home | The section at the top (`FoldAnchor` on the heading, Coming up, Recently added, the kinds, the All titles card: the same ids in the narrow and wide layouts). Coming up's centred card: the folded and open rows are two views, so the new one opens on the card the other had, read from a timed log in `FoldKeep` from before the resize (the old row can re-centre on its first card as it goes), else `v2.home.comingUpFocus`; the opening hold (`V2CarouselOpening`) is unchanged. |
| All titles | The push (`AppModel.allTitles`, `AllTitlesPush`): a stack rebuilt under it drops the page while the window still wants it, and Home, on screen, puts the same push back (`keepPushed`). The grid's scroll keeps the topmost title's row when the columns change (`LibraryOnScreen.anchorRow`). |
| Account | Kept in the Web layout (one sheet both ways). In the Spread layout it moves between a sheet and both pages: Watchlists & lists (pushed folded, the right page open) and the source pushed in it ride in `AccountFoldPlace` (`FoldKeep`, dropped when Account closes), written only by the page on screen; the new host opens them again through the link path. |

Not yet: on the flat open Duo, a sibling picked in a season or episode's
left column swaps the right page in place without changing the path, so
folding lands on the page first pushed; Account's scroll and a pushed
source detail's scroll; Audit and Indexers' list scroll (v1's rows). None
of this is checked on a device yet.

## Shipping

CI builds both schemes as a matrix (`.github/workflows/build.yml`). A separate
`release` job publishes `build-N` with `Fusionha.ipa`, `FusionhaV2.ipa` and one
`source.json` (`scripts/release_source.sh` → `scripts/make_source.py`). v1 is
required. If the v2 leg fails, the job carries v2's entry over from the previous
release's source.json, so v2 stays listed in Feather. The source's identifier and
URL don't change.

The screenshots, iPhone Duo and perf jobs build only the v1 scheme for now.

Before the first install, the owner registers the v2 App IDs and the
`group.org.elabx.fusionha.v2` App Group on the developer account.

## Visual system (slices S1 and S2)

- **Badge state** (`FusionhaKit/EditionBadgeState.swift`): on disk / partial
  (n of m) / missing / downloading (progress) / held, from a coverage `Rail`
  plus the version's `QueueProgress`, or from a wire `EditionStatus`.
  Upgrading reads as downloading; attention, dead links and held imports read
  as held. `EditionBadgeState.joins` (both on disk or both missing) decides
  the spoken pair; the drawn pair joins when both halves draw alike with
  nothing beside them, so with counts hidden partial joins on disk.
  `EditionBadgeSpeech` gives VoiceOver its words.
- **Badges** (`Shared/Design/Badges/`): option A media badges (owner
  2026-11-06). `MediaBadgeView` draws one 25×15pt rounded rectangle (30 wide
  when held) with heavy 9.6pt letters: solid with the letters knocked out (on
  disk), a 1pt half-strength outline (missing), an outline filling with the
  accent left to right as it downloads (0.15 when there is no figure yet),
  orange outline with "!" inside (held). `EditionTicketPair` the HD/4K pair
  (one `CombinedMediaBadge` with a hairline seam when both are on disk, both
  missing or both downloading, owner 2026-11-07; 4pt apart when they differ), `EditionBadge` a
  single version. They draw in a
  `BadgeInk` (`Shared/Design/BadgeInk.swift`): `.page` (any palette),
  `.tinted(ink:ground:)` for art-tinted pages, `.onArt` over artwork, set with
  `.badgeInk(_:)`. They live in `Shared` so v2's widgets can use them; v1
  only uses the pair in its Calendar list rows.
- **Rails** (`App/V2/Components/Rails/`): one ink, from `OneInkRail`.
  `RailBarV2` (season capsule or download progress), `EpisodeTicks` (one tick
  per episode up to 26, or the capsule when the row is too narrow) and
  `StorageCapsule` (stacked storage bar and legend). Held is the palette's
  `stuck` in rails as well as badges: one orange, where the mock's rails use
  #FF9F0A / #FF9500 (deliberate). On the achromatic palettes (OLED, Noir,
  Monochrome, `BadgeInk.patterned`) the accent and held inks sit on the
  on-disk grey, so rails draw downloading as accent hatching on the track and
  held as a held-ink outline.
- **Art palette maths** (`FusionhaKit/PaletteMath.swift`): RGB↔HSL, 12 hue
  buckets weighted by vividness, the top three, the dark and light lift
  clamps, and the page tints. Slice S3 adds the extractor and the ground (below).
- **Badge gallery**: Account (or You) › fusionha v2 › Badge gallery, in v2's
  Release builds too. It shows every state on every palette, at the default
  size and at a large Dynamic Type size, plus the joined/apart animation.

## Art palette ground and W1 cards (slice S3)

- **Extractor** (`App/Components/Images/ArtPaletteExtractor.swift`): an actor.
  It takes the art through `ImagePipeline` (the w780 copy the hero's ambient
  already loads, `ArtPaletteExtractor.sampleURL`), stretches it into a 40×40
  sRGB bitmap off the main thread, and keeps `PaletteMath.dominant`'s three
  colours *before* the lift in an NSCache plus a small JSON disk cache
  (Caches/ArtPalette, one file per URL hash). The lift runs per palette, so a
  palette switch never re-reads the art. "Reset cache & reload" clears it.
- **Page palette** (`Shared/Design/PagePalette.swift`): `\.pagePalette`
  carries the ground recipe, the page tints (the mock's --tint / --tint2), the
  text inks (--tintink / --tintmut) and the badge ink (`BadgeInk.tinted`).
  With no art it is built from the palette's tokens. Hue-less palettes
  (Monochrome, Noir, OLED: `PagePalette.dropsHue`) lift with s = 0, so their
  grounds stay grey.
- **Ground** (`App/V2/Components/Ground/`): `PageGround` draws
  `FusionhaKit/PageGroundRecipe` (a base in the lifted art colours, never
  the page's near-black, under four soft ellipses reaching every corner;
  OLED and Noir `deep`: dark but tinted; `.page` and the deeper `.listPane`
  for the open Duo's list), plus the art itself blurred across the top (the
  Library's ambient layers screen-blend on dark palettes, so a dark side of
  the art never blacks out that side of the page) (`ArtBlurSpec.pageGround`: blur 46, saturate
  1.7, a cached bitmap, no live blur). No art: the token tint ground
  (cards-w.js `.w1-tint`, from i1 / grab / edition). Pages call
  `.v2PageGround(art:)`; `PageArtSource` / `V2Page.groundSource` is the
  mock's `GROUND` map of which art each page uses.
- **W1 cards** (`App/V2/Components/Cards/`): `.v2CardStyle()` and
  `WidgetModule` (caption inside, rows split by hairlines). Ultra-thin
  material plus the mock's wash (rgba(30,30,38,.40) dark, white .58 light),
  a 0.5pt top light edge, 22pt corners, no stroke, and one pre-blurred
  nine-slice shadow with the card cut out of it, so it never darkens the
  translucent card. This is material, not Liquid Glass (owner, 2026-11-05).
- **Ground preview**: Account (or You) › fusionha v2 › Ground preview: any
  library title's ground (or the tint ground), in any palette, page or list
  pane, with modules on it, and three titles side by side.

- **Open issues (shipped with these, 2026-11-07):**
  - The programmatic push into All titles is unreliable at launch. This
    covers the routes (`pendingAllTitles`) and the restore of a kept All
    titles. In CI it sometimes stays on Home, and sometimes hangs the main
    thread in the update that presents the page. A DEBUG readout showed the
    clock stopped as `allTitlesShown` was set, in both palettes.
  - Mitigations in place:
    - routes and restores push without animation;
    - routes wait for the first library load;
    - one idempotent path (`AppModel.allTitles`, `AllTitlesPush`, unit-tested):
      a tap, a route or a restore opens it once (a second ask while it is
      pushed or on its way does nothing); the stack's binding only pops it;
      Back closes it once and stays closed;
    - a route is taken once: by Home (then it opens), or by All titles when
      it is already up, so Back never finds it still set;
    - the relaunch restore runs once per Home (a `.task` runs on every
      appear, and after Back it could re-push);
    - a push the stack dropped is put back while Home is on screen
      (`keepPushed`, a few checks a second apart, binding false then true),
      never closing it;
    - the entry is one-way, never written back into Home mid-push.
  - The last mitigation (one-way entry) was not yet measured. The
    ALLTITLES shots (`library-folded`, `all-titles-*`) are off until this
    lands.

  so it always fits under the arrow.

  item, SwiftUI's geometry for it is in the bar's own space, and the
  system moves it as the column's status items come and go. A passive
  recognizer on the window notes the control under each touch in window
  coordinates; the pill opens from that. On a fold or unfold the pill goes
  at once and returns on the arrow's new spot, found by the bar item's
  title ("Tabs"); if it can't be found it stays closed. The same
  recognizer reports drags (it can neither prevent nor be prevented by
  another recognizer, or a scroll view's pan fails it first).
